# Capacités ARM64 pertinentes pour l'exécuteur FoldGPT

Inventaire du 7 septembre 2026, établi sur PC à partir des preuves et sources
conservées et du relevé descriptif v2 fourni par la tâche principale,
horodaté **7 septembre 00:52:19 +02:00** (`2026-09-06T22:52:19Z`) [E7].
**Il ne décrit pas chaque instruction ARM ni tous les blocs du
SoC Samsung.** Il distingue ce que l'architecture définit, ce que Linux/Android
expose au code utilisateur et ce qui a réellement été vérifié sur ce Fold.
Aucun test d'instruction ni accès au téléphone n'a été effectué par cette
sous-tâche. Le relevé de la tâche principale est en lecture seule.

Le fait décisif est que **le processeur ARM64 n'implémente pas les namespaces
Linux**. Il fournit calcul, mémoire et niveaux de privilège. Les namespaces
sont du code du noyau, choisi à sa compilation. Une instruction accélérée ou
un nouveau programme ARM64 ne peut pas ajouter une branche absente du noyau
protégé déjà démarré.

## Architecture, noyau et droits

| Mécanisme | Définition et exposition | Droit d'un programme Android ou shell | Preuve Fold / limite |
| --- | --- | --- | --- |
| AArch64/A64, registres et ABI | Instructions 64 bits et conventions d'appel AAPCS64 ; ABI Android `arm64-v8a` avec Bionic | Le programme s'exécute nativement dans son processus, selon ses droits Android | **Observé** : `machine=aarch64`, exécutables et bibliothèques AArch64 réels [E1,E2]. Pas d'émulation CPU nécessaire pour du code ARM64 compatible |
| EL0 | Niveau utilisateur de l'architecture | Code de l'application ; le shell reste du code utilisateur lui aussi. UID 0, UID shell et UID app sont des identités logicielles Linux, pas des niveaux EL différents | **Établi par le modèle Linux/Android** ; app Zygote UID 10412/seccomp 2, shell UID 2000/seccomp 0, capabilities effectives nulles dans les deux contextes [E7]. Une API ou JNI ne fait pas passer l'app en EL1 |
| EL1 | Niveau privilégié typiquement utilisé par le noyau ; l'organisation exacte peut varier avec l'hyperviseur/VHE | Le noyau traite une demande et applique ses contrôles ; le programme utilisateur ne choisit pas d'y exécuter du code arbitraire | **Pas de relevé des niveaux EL Samsung**. Inutile d'en déduire un droit de modification du noyau |
| EL2 et virtualisation matérielle | Niveau d'hyperviseur lorsqu'il est présent ; prise en charge de virtualisation et de traduction mémoire supplémentaire | Son existence ne donne pas accès à KVM/AVF ni droit de créer un invité. Cela dépend du noyau, du service système et de la politique | **Observé** : `CONFIG_KVM=y`, sans preuve d'accès applicatif. Une VM sur le téléphone est hors objectif [E1] |
| EL3 / moniteur sécurisé | Niveau privilégié associé au moniteur et aux transitions des états de sécurité lorsqu'il est implémenté | Non accessible comme moteur applicatif arbitraire. Une interface vers un composant sécurisé n'autorise que son service documenté | **Non inventorié matériellement sur ce Fold**. Aucun chargement de code sécurisé envisagé |
| MMU et tables de pages | Traduction adresses virtuelles/physiques et protections gérées par le noyau/hyperviseur | `mmap`/`mprotect` demandent une opération au noyau ; l'app ne remplace pas ses tables de pages ni celles du système | **Observé** : pages système de 4 096 octets, confirmées par `AT_PAGESZ=0x1000` [E7]. Ce n'est ni une allocation de RAM pour une VM ni un droit sur la mémoire physique |
| `SVC` et ABI des appels système | AArch64 fournit l'exception de service ; Linux choisit numéros, arguments et implémentations | Un syscall reste soumis à UID, capabilities, LSM/SELinux, seccomp et état noyau. Écrire l'instruction directement ne contourne pas ces contrôles | **Observé** : syscalls natifs des fixtures ; `USER_NS`/`PID_NS` non compilés malgré les numéros `clone`/`unshare` présents [E1,E3] |
| Synchronisation et atomiques | Instructions exclusives et extensions atomiques ; le compilateur/runtime fournit le contrat C/C++ approprié | Accessibles si l'ISA et le noyau les exposent ; ne donnent aucun droit de création de namespace | **Annoncé par le noyau** : `HWCAP_ATOMICS=1` ; `HWCAP2_LSE128=0` [E7]. Vrais pthreads/allocations historiques [E3], sans test de toutes les instructions |
| Ordonnancement et multicœur | Linux distribue les threads sur les CPU disponibles ; politiques et quotas s'ajoutent | L'affinité/priorité admise n'implique pas le contrôle de l'ordonnanceur ; les droits du shell ne sont pas un droit EL2 | **Observé** : CPU possibles `0-7` [E1]. Aucun benchmark ni droit temps réel déduit |

Les niveaux EL ci-dessus décrivent le modèle architectural, pas une preuve de
la configuration de chaque monde de sécurité ou de chaque firmware du SM8850.
Le protocole de démarrage ARM64 Linux documente explicitement les entrées
possibles EL1/EL2 et les contrôles des niveaux supérieurs [L2]. Il ne décrit
pas le firmware exact de notre Samsung.

## Instructions optionnelles : annonces mesurées du noyau

Le noyau publie ses possibilités de code utilisateur par `AT_HWCAP` et
`AT_HWCAP2`, lus avec `getauxval`. Le NDK fournit les noms de bits dans
`asm/hwcap.h`. **Un nom dans cet en-tête n'est pas un bit mesuré sur le
téléphone.** La documentation Linux recommande de vérifier ces flags ; essayer
une instruction en attendant un `SIGILL` n'est pas une méthode fiable [L1].

Le nouveau relevé v2 E7 conserve l'auxv du processus de lecture lancé depuis
le shell, ainsi que `/proc/cpuinfo` et la configuration noyau complète :

```text
AT_HWCAP  = 0x00000000ffffffff
AT_HWCAP2 = 0x000040003cbb73ef
AT_PAGESZ = 0x0000000000001000
```

Le décodage local avec l'en-tête NDK r29 donne **32 bits HWCAP et 23 bits
HWCAP2 définis et positionnés**. Aucun bit positionné n'est inconnu de cet
en-tête. Ce sont des fonctionnalités **annoncées par le noyau à ce processus
utilisateur**, et non 55 tests d'instructions réussis ni 55 droits nouveaux.
La liste `Features` conservée pour les CPU corrobore ces familles. Les tailles
de vecteur SVE/SME, l'activation du durcissement pour chaque ELF et les
performances de ces extensions n'ont pas été mesurées.

| Famille | Exposition Linux/NDK pertinente | Usage possible pour FoldGPT | État spécifique au Fold |
| --- | --- | --- | --- |
| Flottants et Advanced SIMD/NEON | `HWCAP_FP`, `HWCAP_ASIMD` ; vecteurs courts décrits par AAPCS64 | Calcul, bibliothèques et accélération d'opérations de données | **Annoncés** ; FP16 et plusieurs extensions SIMD également positionnés. Aucun benchmark d'instruction |
| LSE / atomiques étendues | `HWCAP_ATOMICS`, extensions supplémentaires en HWCAP2 | Synchronisation optimisée, sélection du chemin par compilateur/runtime | **LSE annoncé**, LSE128 non annoncé. Ne pas forcer une extension à partir du nom SM8850 |
| AES et multiplication polynomiale | `HWCAP_AES`, `HWCAP_PMULL` | Cryptographie native si la bibliothèque fait une détection correcte | **Annoncés** ; aucune incidence sur les droits noyau |
| SHA/CRC | `HWCAP_SHA1`, `HWCAP_SHA2`, `HWCAP_SHA3`, `HWCAP_SHA512`, `HWCAP_CRC32` | Hashs, intégrité, compression/réseau selon l'outil | **Tous annoncés**. Un hash d'artefact ne prouve pas qu'une instruction matérielle précise l'a calculé |
| SVE/SVE2 | `HWCAP_SVE`, `HWCAP2_SVE2` et variantes ; état et longueur vectorielle gérés par Linux | Calcul vectoriel de certains outils | **SVE/SVE2 annoncés**, avec AES, PMULL, SHA3, SM4, I8MM, BF16. SVE2.1, SVEBITPERM, SVEF32MM/SVEF64MM non annoncés |
| SME et variantes | `HWCAP2_SME`, `HWCAP2_SME2`, etc. | Calcul matriciel si le CPU, le noyau et l'ABI l'exposent | **SME annoncé** avec I8I32, F16F32, B16F32, F32F32. SME2/SME2.1, I16I64, F64F64 et FA64 non annoncés |
| Authentification de pointeurs | `HWCAP_PACA`, `HWCAP_PACG` | Durcissement du code et de certaines adresses de contrôle | **PACA/PACG annoncés** ; activation par chaque runtime non vérifiée. Ne remplace ni politique fichiers ni isolation de processus |
| BTI | `HWCAP2_BTI`, propriétés ELF et comportement du chargeur | Durcissement des destinations de branchement | **Annoncé** ; cela ne prouve pas BTI actif pour chaque ELF |
| MTE / mémoire étiquetée | `HWCAP2_MTE`, `HWCAP2_MTE3` et activation par le système/processus | Détection de certaines erreurs mémoire | **MTE/MTE3 non annoncés dans cet auxv**, malgré `CONFIG_ARM64_MTE=y`. Ni le matériel complet ni les autres contextes ne sont déduits de ce constat. Les propriétés Android ne prouvent pas MTE actif |
| Générateur matériel aléatoire | `HWCAP2_RNG` pour l'extension ISA ; services du noyau distincts | Bibliothèques cryptographiques ; `getrandom` reste l'API système usuelle | **RNG annoncé**. Aucun exercice des instructions RNG ; le fonctionnement de `getrandom` est une preuve différente |

Décodage complet des **bits positionnés**, selon le dictionnaire N1 :

```text
HWCAP (préfixe HWCAP_ omis, bits 0 à 31 tous positionnés) :
FP ASIMD EVTSTRM AES PMULL SHA1 SHA2 CRC32 ATOMICS FPHP ASIMDHP
CPUID ASIMDRDM JSCVT FCMA LRCPC DCPOP SHA3 SM3 SM4 ASIMDDP SHA512
SVE ASIMDFHM DIT USCAT ILRCPC FLAGM SSBS SB PACA PACG

HWCAP2 (préfixe HWCAP2_ omis) :
DCPODP SVE2 SVEAES SVEPMULL SVESHA3 SVESM4 FLAGM2 FRINT SVEI8MM
SVEBF16 I8MM BF16 RNG BTI ECV AFP RPRES SME SME_I8I32 SME_F16F32
SME_B16F32 SME_F32F32 LRCPC3
```

Tous les autres bits définis dans le `hwcap.h` NDK r29 retenu sont à zéro
dans ce relevé. « Non annoncé » signifie que le logiciel ne doit pas supposer
cette fonctionnalité sur la base de cet auxv ; ce n'est pas une preuve que
le silicium ne l'implémente nulle part. `CONFIG_ARM64_SVE=y`,
`CONFIG_ARM64_SME=y`, `CONFIG_ARM64_PTR_AUTH=y` et `CONFIG_ARM64_BTI=y`
concordent avec plusieurs annonces, mais **la configuration compilée seule
ne suffirait pas**, comme le montre MTE.

Le [catalogue CSV complet HWCAP/HWCAP2](catalogs/arm64-hwcaps-ndk-r29.csv)
conserve **les 96 noms définis**, numéro de bit, masque, champ auxv, valeur
observée et booléen `announced`. Les empreintes des deux catalogues, de leurs
en-têtes sources et du relevé Android sont dans le
[manifeste de provenance](catalogs/arm64-ndk-r29-sources.json).
Cela rend les 55 annonces et les 41 bits non annoncés vérifiables sans nouvelle
sonde. Les éventuels bits nommés par un NDK ultérieur ne sont pas inventés ici.

Le GPU Adreno et les autres accélérateurs du SoC ne sont pas des instructions
du CPU AArch64. Le GPU `Adreno840v2` a été lu dans sysfs [E1]. Les APIs Vulkan/
OpenGL ES de la fiche constructeur n'établissent ni chaque extension du pilote
installé, ni l'accès à toutes ses interfaces, ni une capacité d'isolation Linux.
Le DSP/NPU/modem/TEE n'ont pas fait l'objet d'un audit exhaustif ici ; aucun
de ces blocs n'a une voie applicative identifiée qui ajoute les namespaces
manquants au noyau hôte.

## Ce qu'une reconstruction ARM64 peut réellement apporter

- **Oui :** compiler notre superviseur, un interpréteur et ses bibliothèques
  pour Bionic, avec un ensemble d'instructions compatible, puis appliquer les
  mécanismes de droits effectivement fournis par Android.
- **Oui, sous validation :** reconstruire les services attendus par les outils
  au niveau utilisateur, par exemple médiation des fichiers et supervision des
  descendants, avec un contrat et des refus réels. Ce n'est pas créer un PID
  namespace ; les garanties doivent porter leur vrai nom.
- **Non dans le périmètre actuel :** ajouter depuis un APK du code EL1 dans le
  noyau protégé pour réactiver `CONFIG_USER_NS`/`CONFIG_PID_NS`. Ces options
  Linux sont intégrées à la compilation, pas des instructions ARM facultatives
  que l'on pourrait remplacer par une bibliothèque [E4].

Un exécuteur natif Bionic évite le besoin de traduire en permanence les chemins
GNU via PRoot dans la commande. Cela réduit une composition à qualifier, sans
prouver que les deux redémarrages sont corrigés. Les tests PC de CLI Python et
les ELF déjà compilés ne remplacent pas le test final d'un projet créé, testé
et construit depuis l'interface ordinaire du Fold [E5,E6].
